## 분석 — 문제 재정의(PR)와 다차원 분석(MDA)

이번 문제는 “업데이트 버튼이 작동하지 않는다”는 현상에서 출발했지만, 실제로는 외부 데이터 계약, 내부 데이터 정확성, 실행 환경, 성공 상태 관리, 예약 실행을 함께 다뤄야 하는 문제였다. 문제 재정의 관점에서 목표를 “버튼 클릭 후 숫자를 추가한다”에서 “사용자가 어느 로또 화면을 열어도 검증된 당첨 이력을 사용하고, 실패를 성공으로 오인하지 않으며, 다음 갱신 기회를 스스로 확보한다”로 설정했다. 이 구분이 필요한 이유는 마지막 회차만 추가해도 잘못된 과거 데이터와 재시도 지연이 그대로 남을 수 있기 때문이다. 데이터가 최신이라는 판단에는 최신 회차 도달뿐 아니라 중간 회차 누락 여부와 각 회차의 번호·날짜 유효성도 포함돼야 한다.

인과 차원에서는 기존 동행복권 조회 주소와 보조 사이트 파서가 모두 현재 응답 구조와 어긋나는 것을 확인했다. 공식 결과 화면의 스크립트는 새로운 JSON 조회 경로를 사용한다. 보조 사이트는 화면 텍스트에서 번호를 추출하던 방식과 달리 Next.js 구조화 응답에 회차 목록을 담고 있다. 따라서 공개 프록시를 더 추가하는 처방만으로는 정상화되지 않는다. 서버에서 공식 응답을 표준 회차 객체로 변환하고, 보조 소스도 실제 확인한 구조에 맞춰 파싱해야 한다. 통신 오류, 구조 변경, 아직 제공되지 않은 결과를 같은 “새 회차 없음”으로 취급하지 않는 것도 중요하다.

시간 차원에서는 기존 코드가 실패한 갱신에도 마지막 조회 시각을 저장하고, 다음 자동 갱신은 7일이 지나야 수행하도록 구성된 점이 문제였다. 토요일 단 한 번의 실패가 다음 주까지 이어질 수 있는 구조다. 수정에서는 마지막 시도와 마지막 성공을 구분하고, 한국 시간 토요일 21시 35분을 결과 확인 시작 기준으로 삼았다. 화면이 열려 있을 때는 주기적으로 상태를 확인하며 실패 후에는 5분 간격으로 다시 시도한다. 화면 복귀와 인터넷 재연결도 확인 계기로 삼는다. 이 시각은 앱의 운영 기준이며 공식 발표가 항상 그 시각에 끝난다는 보장은 아니다.

계층 차원에서는 브라우저 캐시, 두 React 화면, 공통 데이터 파일, 서버 API, 저장소 예약 작업의 책임을 분리했다. 기존 분석 화면은 내장 회차 이후만 조회하며 과거 누락 부분에는 난수로 생성한 데이터를 넣고 있었다. 다른 화면은 별도 기본 배열을 사용해 서로 다른 빈도 계산 결과가 나올 수 있었다. 이번에는 공식 API로 1회부터 1249회까지 전체를 수집해 단일 파일로 만들고, 두 화면이 이를 함께 사용하게 변경했다. 기존 캐시는 다른 키로 분리하여 과거 잘못된 값이 새 공식 스냅샷을 덮어쓰지 않게 했다. 누구나 입력 가능한 공유 저장소 역시 공식 정본으로 취급하지 않도록 현재 화면 경로에서 제외했다.

공간·환경 차원에서는 개발 환경과 배포 환경의 실행 차이를 확인했다. Vite 자체는 Vercel 함수 파일을 자동 실행하지 않으므로 개발 서버에서 API 경로를 호출해도 같은 동작을 기대할 수 없었다. 동일한 서버 함수를 Vite 개발 및 미리보기 서버의 미들웨어로 연결했고 두 설정 파일에 반영했다. 배포 환경에서는 기존 `/api/lotto` 경로를 유지한다. 이로써 로컬에서 정상인 경로와 실제 배포 경로 사이의 차이를 줄였다. 다만 이번 검증은 로컬 API, 실제 외부 응답, React 서버 렌더링까지이며 브라우저 호스트가 제공되지 않아 클릭 기반 화면 검증은 수행하지 못했다.

종합하면 복구의 중심은 더 많은 요청을 보내는 데 있지 않고, 올바른 출처·검증·완료 판단·재시도 조건을 일관되게 정의하는 데 있다. 공식 데이터 전체를 다시 받았으며 회차 연속성, 번호 범위, 중복, 보너스 번호, 추첨일을 검사했다. 새 파일은 완전한 검증 후에만 교체한다. 예약 작업 설정과 로컬 실행 코드는 준비했지만 원격 저장소 반영이나 배포는 수행하지 않았다. 따라서 “자동 업데이트 코드가 준비됐다”와 “운영 환경에서 예약 실행이 확인됐다”는 서로 다른 상태로 기록한다.

## 개선 아이디어 10개 — 적용 결과와 후속 선택지

1. **회차를 단위로 한 데이터 계약 — 적용.** 모든 출처의 데이터를 `{drw, nums, bonus, date}` 형태로 통일한다. 화면별로 다른 응답 속성을 해석하게 두면 한쪽만 수정되는 문제가 반복될 수 있다. 번호 여섯 개와 보너스까지 총 일곱 개가 서로 다르고 정수이며 1~45 범위인지 확인한다. 추첨일은 첫 추첨일과 주간 간격을 기준으로 검사한다. 이 검사는 번호가 공식 결과와 동일함을 증명하는 절차와는 구분해야 한다. 형식 검사는 저장 가능한 데이터인지 판단하고, 공식 출처 조회는 그 값의 근거를 제공한다. 두 조건을 함께 유지하는 것이 핵심이다.

2. **과거 이력을 포함한 정본 재구축 — 적용.** 마지막 회차만 갱신하면 오래된 임의 데이터가 통계에 계속 영향을 준다. 공식 API 전체 조회를 통해 1회부터 현재 회차까지 연속된 스냅샷을 만들고 추천·빈도·최근 결과가 같은 자료를 보도록 한다. 파일 생성기는 회차가 하나라도 빠져 있으면 기존 파일을 교체하지 않는다. 이를 통해 일시 장애가 정상 스냅샷을 불완전한 데이터로 덮는 일을 방지한다. 향후 공식 수정 공지가 있는 경우에는 별도 전체 재수집 절차를 추가해 과거 정정까지 반영할 수 있다. 현재 정기 스크립트는 신규 회차를 중심으로 갱신한다.

3. **성공과 시도를 별도 기록 — 적용.** 통신을 시작했다는 사실은 최신 정보를 얻었다는 뜻이 아니다. 기존에는 실패도 마지막 갱신 시각에 반영돼 재시도가 지연됐다. 새 구조는 성공적으로 받은 데이터가 예상 회차까지 연속되는 경우에만 성공 시각을 저장한다. 자동 시도 간격은 별도 메모리 상태로 관리하고, 화면에는 실패와 재시도 안내를 보여준다. 다음 단계로 운영 기록을 확장한다면 마지막 시도 시각, 마지막 성공 시각, 누락 회차 수를 각각 표시할 수 있다. 이 정보는 사용자가 수동 재시도를 할지 기다릴지 판단하는 데 직접 도움이 된다.

4. **주간 단일 타이머에서 복구 가능한 갱신으로 전환 — 적용.** 토요일 한 번의 타이머는 노트북 절전, 탭 중단, 네트워크 단절에 취약하다. 결과 확인 시각 이후 예상 최신 회차를 계산하고, 화면이 보일 때 주기적으로 확인하도록 바꾼다. 탭 복귀와 인터넷 재연결도 확인 계기로 사용한다. 실패하면 5분 간격으로 재시도하고 이미 최신인 경우는 불필요한 빈번한 요청을 줄인다. 이 구조는 특정 시각의 실행 여부보다 실제 데이터 상태를 중심으로 동작한다. 실제 호출 시점은 브라우저 타이머 제한에 영향을 받을 수 있어 초 단위 실행 보장으로 표현하지 않는다.

5. **같은 요청을 함께 기다리는 중복 방지 — 적용.** 자동 갱신과 버튼 클릭이 겹치거나 개발 모드에서 효과가 반복 실행되면 같은 조회가 중복될 수 있다. 진행 중인 Promise를 공유하면 여러 호출자가 하나의 네트워크 요청 결과를 기다릴 수 있다. 이는 외부 서버 부하를 줄이는 동시에 늦게 도착한 응답이 최신 화면을 덮는 경쟁 조건을 줄여 준다. 실패 후에는 진행 상태를 반드시 해제해 다음 시도가 가능하도록 한다. 회귀 테스트는 두 호출이 같은 Promise를 받는지와 실패 뒤 새 요청이 가능한지를 확인한다. 향후 여러 탭 사이의 요청 공유는 별도 조정 계층으로 확장할 수 있다.

6. **공식 스냅샷을 우선하는 캐시 이행 — 적용.** 과거 캐시가 있다는 이유만으로 그것을 신뢰하면 잘못된 기본 데이터가 오래 남을 수 있다. 새 버전 키를 사용해 기존 저장값을 분리하고, 공식 파일에 존재하는 회차는 그 파일의 값을 우선한다. 이후 신규 회차는 공식 API 결과로 보완한다. 수동 입력은 로컬 보조 기능으로 남기되 전역 정본으로 자동 전파하지 않는다. 입력 시점에는 정수·중복·회차 날짜를 검증하고, 다음 공식 조회에서 확인할 수 있도록 한다. 브라우저 저장 공간이 막혀도 화면에서 공식 기본 데이터를 사용하는 경로는 유지한다.

7. **개발·미리보기·배포에서 같은 서버 함수 사용 — 적용.** 환경별 프록시가 서로 다른 구현을 갖고 있으면 문제가 어디서 발생하는지 추적하기 어렵다. Vite 미들웨어가 실제 서버 함수에 요청을 전달하도록 연결해 로컬에서도 동일한 데이터 변환과 오류 응답을 사용한다. 사용자 화면은 외부 프록시 목록 대신 같은 출처의 API만 호출한다. 개발 검증은 실제 로컬 API에 요청해 JSON 응답과 최신 회차를 확인하는 방식으로 수행했다. 이후 배포 검증에서는 동일 요청을 운영 도메인에 보내 응답 상태, 실행 시간, 최신 회차를 비교하면 환경 차이를 빠르게 좁힐 수 있다.

8. **브라우저와 독립된 데이터 파일 예약 갱신 — 설정 추가.** 페이지가 닫혀 있는 동안에도 데이터 파일을 갱신하려면 브라우저 밖의 실행 주체가 필요하다. GitHub Actions에 토요일 저녁 두 차례, 일요일 새벽 및 일일 복구 일정을 추가했다. 실행은 공식 데이터를 검증하고 테스트가 통과한 경우 변경된 JSON 파일만 커밋하도록 구성했다. 같은 예약 작업끼리는 동시에 파일을 수정하지 않게 했다. 이 설정은 기본 브랜치에 반영되고 저장소의 Actions 실행 및 쓰기 권한이 허용되어야 작동한다. 보호 브랜치 정책과 배포 연동 여부도 운영에서 확인할 항목이며 이번에는 원격 설정을 바꾸지 않았다.

9. **보조 소스는 제한을 명시한 복구 경로로 사용 — 적용.** 보조 사이트의 최신 목록은 전체 과거 데이터와 동일한 범위를 보장하지 않는다. 현재 확인한 구조화 목록에서 번호를 읽되 스크립트를 실행하지 않고 JSON만 해석한다. 공식 조회 중 장애가 나면 이 자료로 보완할 수 있지만, 필요한 중간 회차가 빠져 있으면 완료로 처리하지 않는다. 이런 설계는 보조 데이터가 있다는 이유로 불완전한 갱신을 성공으로 표시하는 문제를 막는다. 향후 안정성이 더 필요하면 별도 출처를 추가하되 출처 간 불일치 처리 규칙을 먼저 정하고, 어느 값이 선택됐는지 운영 기록에 남기는 방법을 검토할 수 있다.

10. **장애 조건을 중심으로 한 회귀 검증 — 적용 및 확장 제안.** 단순히 정상 응답 한 건을 확인하는 것만으로 자동 갱신을 검증하기는 어렵다. 이번 테스트는 한국 시간 경계, 데이터 연속성, 중복 번호, 잘못된 날짜, 통신 실패, 잘못된 쿼리, 중복 요청과 성공 기록을 다룬다. 실제 API에서 19개 회차를 가져오는 호출과 두 React 화면의 렌더링도 확인했다. 다음 운영 단계에서는 예약 작업을 수동 실행해 생성된 커밋과 배포 결과를 확인하고, 실패 알림을 팀의 기존 운영 채널과 연결할 수 있다. 알림 전송이나 외부 채널 변경은 이번 작업에 포함하지 않았다. 장기적으로는 출처 변경을 빨리 감지하는 작은 정기 진단을 더할 수 있다.
